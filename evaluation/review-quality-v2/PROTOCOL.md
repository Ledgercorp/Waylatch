# Review-quality v2 protocol — defined before predictions

This is a new synthetic evaluation. Original evaluation files, frozen manifest, completion receipt, scoring implementation and all reported v1 numbers must remain unchanged. V1's exposed examples may motivate this work but do not validate it independently.

## Question and predetermined success criteria

Compare v1 combined `createReviewer` against the revised advisory strategy on the same genuine pinned local MiniLM vectors and candidate pairs. Primary binary attention flag: revised **needs-verification OR strong-duplicate-evidence**, versus v1 `reviewRecommended`. Potentially-related is informational retrieval and does not count as an attention alert. Strong is separately reported as high priority; both alert definitions must stay visible.

Primary success requires ALL of: (1) at least 50% lower false-positive rate for attention than v1, (2) no more than 10 attention alerts per 100 labeled distinct pairs, (3) at least 0.50 recall for labeled duplicate pairs. These values are chosen before any v2 predictions. Strong-tier precision target is at least 0.80 (undefined precision fails this target). These are engineering targets on synthetic data, not operational requirements or prevalence estimates. Failure remains failure; do not select different favorable metrics afterward.

Report TP/FP/FN/TN, precision/recall/F1, FPR=FP/(FP+TN), attention and strong alerts per 100 distinct pairs, total returned relationships, tier counts and accuracy/confusion against independently annotated records-only evidence tiers. Keep binary transaction identity and records-only tier labels distinct. Ambiguous identity labels are excluded from binary metrics; ambiguous tiers excluded from tier accuracy and retained verbatim.

Budgeted recall: per split, rank all pairs by each method's fixed priority (v1 binary recommendation then cosine; revised tier then supporting evidence then cosine; deterministic case ID breaks ties). Inspect the first floor(0.20*N) nonambiguous pairs. Report duplicate recall, precision and distinct alerts within this fixed 20% review budget. Do not pick a different budget after outcomes. Global candidate-pair ranking is a bounded surrogate, not a multi-candidate query retrieval benchmark; no MAP/NDCG claim without query relevance groups. Report workload counts, not measured human minutes.

Use the existing seeded paired supply-family bootstrap (10,000 draws, seed 20261013) for attention F1 difference, alongside a descriptive paired family bootstrap of FPR/recall/budgeted recall differences when feasible. Few synthetic clusters and common author templates make intervals exploratory, not independent population evidence. Case-level Wilson intervals do not account for cluster dependence.

## New corpus and blind annotation

240 entirely new fictional procurement pairs in 12 new supply families: four families/80 cases calibration, eight other families/160 cases held out. Family and group IDs disjoint between splits. No v1 case, record ID or exact description reused. Scenario author must not read implementations, predictions or old cases. Include hard positives, legitimate repeats, recurring services, different delivery locations, product/specification differences, separate orders on consolidated receipts, conflicting references/receipts, partial/corrected records, missing identity facts and truly identical descriptions for separate transactions. Vary which distinguishing facts are present in records versus scenario-only. Avoid a guaranteed machine-perfect label pattern or forced binary certainty.

Predictor records contain id, incident, description, amountCents, receiptDigest, transactionReference, createdAt, and OPTIONAL existing application facts location, expenseAt and amountKind. No new persisted request/QR fields. Supplier identity and receipt line allocation are absent from this schema; never manufacture them. Every pair must meet application description/field bounds.

Separate fresh AI reviewers receive only shuffled `{id,scenario,left,right}` packets, not split/family/category, code, author intentions, scores or thresholds. Each judges `decision: duplicate|distinct|ambiguous` with rationale. Independently judge `evidenceTier: none|potentially-related|needs-verification|strong-duplicate-evidence|ambiguous` from RECORDS ONLY: none has no meaningful relation; potentially-related is wording/context alone or clues to different transactions; needs-verification has a transaction-linked clue requiring inspection, possibly contradictory/incomplete; strong has multiple corroborating transaction indicators without material recorded contradiction. Shared supplier or receipt document alone is not transaction identity. Labels are nonexpert AI judgments, not human truth; confidence is subjective. Preserve ambiguity and author/reviewer disagreement rather than changing labels to fit code. The author creates no machine label key; scenario facts remain the stated evidence.

Each case receives two independent fresh reviewer judgments. Merge identity disagreements to ambiguous and tier disagreements to ambiguous, without adjudicating toward predictions; preserve both raw judgments and disagreement counts. Join all labels before calibration. Do not expose held-out predictions before freeze. Calibration may inform documented changes; inspect calibration only. Freeze final dataset, annotations, protocol, scorer, runner, model loader/pins, legacy baseline/statistics, settings and package/dependency manifest with SHA-256. The original v1 freeze is never used or overwritten. Use a new exclusive v2 manifest and completion receipt; held-out executes once. No deleting receipts or making another manifest for reruns.

## Runtime and safety

Exact existing Xenova/all-MiniLM-L6-v2 pinned revision/weights, q8 local CPU, 384 finite nonzero dimensions, at most 100 texts per embedding call; no model downloads or paid inference. Reuse genuine vectors for controlled comparison. Missing/corrupt assets block measurements, not simulated semantic scores. Record model load, inference, scoring, wall time, process memory, versions and source fingerprints. Document known API candidate limits and any ordering/truncation effects. No payment/provider calls or mutations in evaluation.

All output remains advisory. No rejection, approval, payment block or transaction is caused by a tier or dismissal. Reports must present the unfavorable original v1 result alongside v2 outcomes, whether the new primary targets pass or fail. New labels, balanced sampling and scenario-only facts limit real-world interpretation.
