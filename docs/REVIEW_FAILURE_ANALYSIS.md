# From similar descriptions to transaction identity

The original frozen evaluation remains unchanged: v1 combined flagged 70/72 labeled distinct held-out pairs (FPR 0.9722), while deterministic flagged 16/72. Its scoring rule is receipt OR reference OR ((semantic>=0.60 OR identical wording) AND (same incident OR amount)). Incident and amount are common across unrelated purchases; they do not identify a delivery. Cosine retrieves language relationships. Treating it as a binary duplicate alert confuses related supplies with the same expense.

| Failure                                         | Observable facts                                                              | Missing or scenario-only facts                                                     | Consequence                                                                                                                                                |
| ----------------------------------------------- | ----------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Repeated purchases / recurring services         | Wording, price, request creation time; expense time if recorded               | Fulfillment records, depletion logs and independent service visits                 | Identical wording can be legitimate; request creation time is not service time.                                                                            |
| Different locations                             | Existing location field, sometimes incident or text                           | Delivery signatures, allocation/transfer/correction explanations                   | Display recorded differences; do not assume a location difference proves distinctness.                                                                     |
| Similar products / different specifications     | Description text, resource quantities and exact/estimated amount              | Product codes, supplier catalog and item-level invoice allocation                  | Language overlap cannot establish product or transaction identity. Quantities remain inspectable but row positions are not reliably comparable identities. |
| Consolidated receipts                           | Same document digest and free-form reference; amount/time may match or differ | Individual line allocations, invoice versus order reference namespace              | A shared receipt can cover multiple purchases, including equal-value lines. Matching digest alone is not proof.                                            |
| Different references / receipts                 | Exact reference strings and receipt-byte digests                              | Whether a reference is unique, corrected or generic; whether two files are rescans | Contradictions and missing corroboration must remain explicit. Different scans need not mean different expenses.                                           |
| Supplier conflicts                              | None in current structured record; sometimes self-declared wording            | Supplier identity, authoritative invoice lookup                                    | No model can recover missing supplier facts. No new supplier field is invented or silently extracted.                                                      |
| Identical descriptions / missing identity facts | Literal wording, incident, amount, location if supplied                       | Whether one or two underlying deliveries actually happened                         | Return informational relationships; neither high cosine nor identical text establishes sameness.                                                           |

The API previously forwarded only seven fields and discarded already stored amountKind, expenseAt and location. V2 forwards these optional facts without changing RequestSchema, IndexedDB, RL1 or QR serialization. Unknown legacy facts remain unknown. It never infers an exact price from an estimate, treats creation timestamps as fulfillment dates, or fabricates missing supplier/line-item data.

The revised strategy separates informational relationships, attention needing verification and strong corroborating evidence. Strong requires a matching recorded receipt, reference, exact amount and expense timestamp, without recorded location/reference/receipt/incident/time/amount contradiction. The fields remain self-declared and may correlate: even strong evidence is advisory and can be wrong for equal-value lines on a consolidated document. Dual matching identifiers with contradictory context require inspection rather than promotion to strong. Single-document/description similarity with contradictory transaction context stays informational.

Candidate ranking uses tier, count of supporting recorded matches, cosine and stable lexical ID. It is not a probability. Grouped summaries replace repeated full warnings; comparison detail shows contradictions ahead of matches and exposes missing corroboration. A current-revision unrelated disposition moves a candidate to the collapsed dismissed group without erasing evidence, changing the scorer or affecting purchase authorization. Revision changes invalidate that dismissal and stale assessment evidence. The existing 100-candidate API cap remains: ranking is among assessed candidates, not proof of full-database retrieval recall. V2 budgeted pair ranking is a surrogate, not query-level MAP/NDCG or measured reviewer minutes.

The exposed old cases informed this information-gap analysis, not independent validation. The v2 protocol, independently authored corpus, blind nonexpert AI labels, calibration decision and once-only held-out receipt establish a separate test. Primary targets must be reported even if they fail; conservative presentation is not a substitute for duplicate recall. No AI finding rejects, blocks, approves or executes a payment.
